[[groovyfx]]
= GroovyFX (incubating)

The optional `groovy-fx` module makes JavaFX groovier. It is a fresh
implementation of the ideas in the original
https://github.com/groovyfx-project/groovyfx[GroovyFX] project, structured
along the same lines as <<swingbuilder,SwingBuilder>>, and it has three parts:

* `SceneGraphBuilder`, a builder that creates stages, scenes, layouts, controls,
  shapes and charts from a nested Groovy DSL;
* `@FXBindable`, an AST transformation that turns plain Groovy properties into
  JavaFX properties;
* extension methods that let JavaFX observable values take part in Groovy
  operators and closures.

The module is incubating: its API may change between minor releases.

== Getting JavaFX

JavaFX is not part of the JDK and is not bundled with Groovy. OpenJFX is
licensed under GPL-2.0 with the Classpath Exception and published as one jar
per platform, so `groovy-fx` compiles against it and expects you to
supply it at runtime. There are several ways to do that, roughly in order of
convenience:

A JDK that includes JavaFX::
Distributions such as Azul Zulu FX and BellSoft Liberica Full ship the
`javafx.*` modules inside the runtime image. On such a JDK nothing further is
needed: `groovy app.groovy` just works, with no module-path flags.

A build tool::
Add the `org.openjfx` artifacts for your platform to your Gradle or Maven
build, for example through the `org.openjfx.javafxplugin` Gradle plugin, which
resolves the platform classifier for you. The published `groovy-fx` module
declares no dependency on OpenJFX at all, not even for compilation, so your
build must list `javafx-base`, `javafx-graphics` and `javafx-controls` itself
before an IDE can resolve the JavaFX types.

The JavaFX SDK::
Download the SDK (for example `sdk install javafx` with SDKMAN) and put it on
the module path through `JAVA_OPTS`:
+
----
export JAVA_OPTS="--module-path /path/to/javafx-sdk/lib --add-modules javafx.controls"
groovy app.groovy
----

Grape::
In a self-contained script, grab the artifacts with the classifier for your
platform (`linux`, `linux-aarch64`, `mac`, `mac-aarch64` or `win`):
+
[source,groovy]
----
@Grab(group='org.openjfx', module='javafx-base', version='21.0.8', classifier='mac-aarch64')
@Grab(group='org.openjfx', module='javafx-graphics', version='21.0.8', classifier='mac-aarch64')
@Grab(group='org.openjfx', module='javafx-controls', version='21.0.8', classifier='mac-aarch64')
----
+
When JavaFX is loaded from the classpath rather than the module path, it
prints a warning about an unsupported configuration; the warning is harmless.

The module is compiled against JavaFX 21, the oldest line that supports JDK
17, and runs against any later JavaFX. Because the builder works reflectively,
controls and properties added in later JavaFX releases are available through
it without any change to the module.

When JavaFX cannot be found, the module fails with a message that repeats the
options above rather than a bare `NoClassDefFoundError`.

application thread. Nothing has to extend `javafx.application.Application`,
which also means a script never trips the launcher's "JavaFX runtime
components are missing" check.

Inside the closure, the first `stage` node without an explicit stage reuses
the primary stage. The `show: true` attribute shows it once its children have
been built.

== Nodes, attributes and children

Every node name maps to a JavaFX class: `vbox` to `VBox`, `button` to
`Button`, `rectangle` to `Rectangle`, `lineChart` to `LineChart` and so on.
A single unnamed argument is passed to a matching constructor, so
`button('Click me')` is `new Button('Click me')` and `tab('Settings')` is
`new Tab('Settings')`. Named attributes are set as properties on the created
node. Nested nodes are attached to their parent according to the parent's
type: panes and groups receive them as children, a `TabPane` receives tabs, a
`MenuBar` menus and a `Menu` items, a `ScrollPane`, `TitledPane` or `Tab`
takes a single content node, a `Stage` takes a `Scene`, any control takes a
`Tooltip` or `ContextMenu`, and a labeled control takes a node as its graphic.

Attribute values receive a few conveniences:

* an `ObservableValue` given for a property *binds* the property to it; when
  the property holds text and the value does not, the value is shown as text
  (`label(text: model.ageProperty())`);
* a list given for an `ObservableList` property (`items`, `styleClass`,
  `transforms`, `stylesheets`, `points`) replaces the list's contents;
* a string is accepted for any `Paint` property (`fill: 'red'`,
  `stroke: '#336699'`);
* a number or a CSS-style list is accepted for `Insets` properties
  (`padding: 10`, `padding: [5, 10]`);
* a size, family or `[family, size]` list is accepted for `Font` properties;
* closures are coerced to the listener types JavaFX expects, so
  `onAction: { ... }` and `onMouseClicked: { event -> ... }` just work;
* an `id` attribute publishes the node as a builder variable (and sets the
  node's CSS id when it has none), so later code can refer to it as
  `builder.name`.

Inside a `gridPane` the constraints are `row`, `column`, `rowSpan`,
`columnSpan`, `hgrow`, `vgrow`, `halignment`, `valignment`, `margin`,
`fillWidth` and `fillHeight`; inside an `hbox` or `vbox` they are `hgrow` or
`vgrow` and `margin`; inside a `stackPane`, `borderPane` or `tilePane`,
`alignment` and `margin`; and inside an `anchorPane`, `topAnchor`,
`bottomAnchor`, `leftAnchor` and `rightAnchor`. A `borderPane` places
children through the `top`, `bottom`, `left`, `right` and `center` nodes. A
constraint name that is also a property of the child, such as `alignment` on
a label, sets the child's property instead.

Existing objects can take part in a builder tree through `node(existing)`
for scene-graph nodes and `bean(existing)` for anything else.

The <<groovy-fx-nodes,node reference>> at the end of this chapter lists every
node name the builder registers, with the JavaFX class it creates. A JavaFX
class without a node name is not a bug in the module: use `node(new Thing())`
for it, or register a factory of your own with `registerBeanFactory`.

== Properties and binding

=== `@FXBindable`

JavaFX binding works on JavaFX properties, which are tedious to write by
hand. The `@FXBindable` transformation generates them from plain Groovy
properties:

[source,groovy]
----
include::../test/GroovyFXSpecTest.groovy[tags=fxbindable,indent=0]
----

For each property `name` of type `T` it generates `getName()`, `setName(T)`
and `nameProperty()`. The property type follows the declared type:
`boolean`, `int`, `long`, `float`, `double` and `String` (and their wrapper
types) become the corresponding JavaFX property types, `short` and `byte`
widen to an `IntegerProperty`, `ObservableList`, `ObservableMap` and
`ObservableSet` become the collection property types, and anything else
(including `char`) becomes an `ObjectProperty`. The JavaFX property object is
created the first time `nameProperty()` is called, so a bean that is never
bound costs no more than a plain Groovy bean. The annotation can be placed on
individual properties or on the class, in which case every non-static,
non-final property is transformed.

`@FXBindable` and Groovy's `@Bindable` both generate the setter, so combining
them on a property is a compile-time error. A bean that must also report
`PropertyChangeEvent`s keeps `@Bindable`, and JavaFX's
`javafx.beans.property.adapter` builders expose any such property as a JavaFX
property, with changes flowing in both directions:

----
include::../test/GroovyFXSpecTest.groovy[tags=fxbindable_adapter,indent=0]

The adapters use `java.beans`, so they need the `java.desktop` module, which
every full JDK provides.

=== Operators on observable values

JavaFX names its fluent binding methods `add`, `subtract`, `divide`, `negate`
and `concat`; Groovy's operators look for `plus`, `minus`, `div`, `negative`
and `plus`. The module supplies the missing names, so arithmetic and string
concatenation on properties yield live bindings:

[source,groovy]
----
include::../test/GroovyFXSpecTest.groovy[tags=operators,indent=0]
----

Two things Groovy's semantics put out of reach are worth knowing. Comparison
operators cannot produce bindings, because Groovy routes `<` and `>` through
`compareTo`; use `greaterThan(...)` and friends for a `BooleanBinding`. And
`!property` applies Groovy truth to the property object itself rather than
calling `not()`, so use `property.not()` for a live negation. `*` and `&`
already work without help, because JavaFX uses the same names as Groovy for
`multiply` and `and`.

A constant operand selects the JavaFX overload for its type: `int` for an
`Integer`, `Short` or `Byte`, `long` for a `Long`, `float` for a `Float` and
`double` for any other number. Groovy's decimal literals are `BigDecimal`, so
`width * 0.5` is computed in `double` precision; JavaFX has no `BigDecimal` or
`BigInteger` overloads.

The `onChange` and `onInvalidate` extension methods register listeners backed
by closures and return the listener for later removal; `onChange` accepts a
closure of one, two or three parameters (the new value; the old and new
values; or the observable and both values).

=== Troubleshooting

`GroovyFX.start`, `fx` and `fxBuilder` all start the toolkit through
`Platform.startup` on first use and are safe to call repeatedly, from any
thread, including when something else has already started JavaFX. Two
situations are reported as an `IllegalStateException`:

The JavaFX toolkit has been shut down and cannot be restarted in this JVM::
`Platform.exit()` was called, or the last window was closed while implicit
exit was enabled; JavaFX cannot be restarted in the same JVM. Call
`Platform.setImplicitExit(false)` when windows come and go, as they do in a
test suite or an interactive session.

The JavaFX toolkit did not start within 30 seconds::
The toolkit could not create its glass platform, most often because there is
no display; see the next section. The wait is configurable through the
`groovyfx.toolkit.timeout` system property, in seconds.

== Testing without a display

The JavaFX toolkit needs a display unless a headless glass platform is
installed. With `org.testfx:openjfx-monocle` on the test classpath, run the
tests with `-Dglass.platform=Monocle -Dmonocle.platform=Headless`; on JavaFX
26 and later the platform ships its own headless implementation, enabled with
`-Dglass.platform=headless`. The module's own tests run this way, on JDK 17
through 25, and need no `--add-opens` or `--add-exports` flags. Note that
property, binding and `@FXBindable` code needs only `javafx.base` and no
toolkit at all.
